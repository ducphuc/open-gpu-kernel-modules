# NVIDIA 610.57.04 P2PDMA and DMA-BUF delta analysis

## Scope and baseline

This analysis compares the official NVIDIA releases `610.43.03`
(`452cec62d827034798072827d3866d1881662b77`) and `610.57.04`
(`e4a5faa2567f28c8eabe0ebb6422b6d0abcf37eb`). It focuses on behavior that
constrains the consumer BAR1 P2P and non-coherent DMA-BUF GDR work. The
official repository publishes each release as a single snapshot commit, so
the delta cannot be separated reliably into upstream topic commits.

## Executive summary

The 610.57.04 release does not replace the existing DMA-BUF export protocol,
but it changes several invariants below it:

1. External read-only OS descriptors now remain read-only through the RM
   memory descriptor and Linux DMA mapping layers.
2. DMA map and unmap directions are stored with each mapping and must match.
3. Partial DMA-BUF physical-address mapping failures now restore per-handle
   reference counts before unwinding mapped handles.
4. Modern kernels using the IOMMU DMA layer are no longer misclassified as
   direct-DMA merely because `get_dma_ops()` returns `NULL`.
5. Imported OS-page-array ownership and parameter provenance are hardened.
6. UVM device-private-memory eligibility is explicit, including CDMM and
   kernel DEVICE_PRIVATE support.
7. P2P capability handling tolerates multiple recommended NVLink copy
   engines by selecting the lowest engine instead of asserting.

These changes mean that a 610.43.03 feature patch cannot be replayed safely by
context alone. It must preserve protection flags, DMA direction, ownership,
and failure-unwind rules introduced in 610.57.04.

## Linux DMA mapping direction

`nv_dma_map_t` now records `bReadOnlyDeviceMap`. The flag is passed through
`nv_dma_map_alloc()`, the page and imported-SGT mapping helpers, and every
contiguous or scatter-gather map operation. `nv_dma_get_direction()` converts
it to:

- `DMA_TO_DEVICE` for a device-read-only mapping; or
- `DMA_BIDIRECTIONAL` for ordinary mappings.

The same stored direction is used for unmap, which is required by the Linux
DMA API. Imported SGTs remain exporter-mapped and are not mapped or unmapped a
second time by this layer.

The RM IOVA path only requests the read-only direction for an external page
array that is not kernel-owned and is marked user-read-only or
device-read-only. Existing RM-owned buffers that reuse the user-read-only bit
remain bidirectional because the kernel may write them. P2P-page remapping
callers in `osapi.c` explicitly pass `NV_FALSE`, preserving bidirectional peer
traffic.

### Porting consequence

New DMA-BUF importer or FORCE_PCIE code must not bypass `nv_dma_map_t`, change
the map direction after mapping, or unmap with a hard-coded direction that
can differ from the stored direction. Any imported OS descriptor flags must
survive through `osCreateMemdescFromPages()` before IOVA mapping begins.

## OS descriptor protection and ownership

The OS-descriptor construction path now makes CPU read-only imports device
read-only as well. `osCreateMemdescFromPages()` sets both
`MEMDESC_FLAGS_USER_READ_ONLY` and `MEMDESC_FLAGS_DEVICE_READ_ONLY` when the
legacy allocation flags require them, and also handles an explicit
device-read-only flag.

The resource constructor additionally:

- translates read-only OS32 attributes into both user and device protection;
- rejects `OS_PAGE_ARRAY` descriptors received directly from user parameter
  memory, because the pointer must have been replaced by a pinned kernel page
  array in the Unix escape layer; and
- clears the returned descriptor after successful page-array or IO-memory
  construction, transferring cleanup ownership to the memory descriptor.

The Unix escape path uses a local copy of allocation parameters while it
temporarily substitutes the pinned kernel pointer. This avoids exposing that
pointer on copyout and avoids a second cleanup after ownership transfers.

### Porting consequence

DMA-BUF changes must preserve the new device-read-only flag and must not add a
second owner for pinned pages, SGTs, or imported descriptor storage. Error
paths must be reviewed for exactly one unpin/free operation.

## IOMMU classification

Linux 6.12 introduced `use_dma_iommu()` for common DMA allocation paths. On
such kernels `get_dma_ops(dev) == NULL` no longer proves that a device uses
direct DMA. The 610.57.04 compatibility layer probes for
`linux/iommu-dma.h` and `use_dma_iommu()`, and `nv_is_dma_direct()` returns
false when that helper reports an IOMMU DMA domain.

### Porting consequence

The old branch's identity-IOMMU and P2PDMA admission checks must be evaluated
on top of this corrected classification. They must not infer identity mapping
solely from a null DMA-ops pointer. Translated IOMMU configurations must remain
fail-closed until their address translation and scatterlist behavior are
explicitly validated.

## DMA-BUF physical-address failure unwind

`nv_dma_buf_get_phys_addresses()` now initializes its progress counter and
handles a partial mapping failure in two stages:

1. It decrements reference counts for the processed prefix before calling
   `nv_put_phys_addresses()`, allowing mappings first created by the failed
   call to reach zero and be unmapped.
2. It separately decrements the unprocessed suffix.

The prior implementation called `nv_put_phys_addresses()` while the failed
call's references were still elevated and then reset the whole range. That
could prevent newly created mappings in the processed prefix from being
unmapped correctly and could destroy valid pre-existing reference state.

### Porting consequence

FORCE_PCIE locking must wrap this corrected per-handle state machine rather
than replacing it. New failure paths must preserve references held by earlier
successful callers and unwind only work owned by the current call.

## UVM devmem and P2PDMA interaction

610.57.04 introduces `uvm_gpu_supports_devmem()` and uses it both during GPU
creation and when an already-created GPU is retained by a VA space requesting
HMM. NUMA-attached and integrated GPUs are excluded from ordinary
ZONE_DEVICE/DEVICE_PRIVATE memory. CDMM devices use their separate mechanism;
other GPUs require kernel DEVICE_PRIVATE `memremap_pages()` support.

This is adjacent to, but distinct from, PCI P2PDMA provider registration.
Both mechanisms can involve device-memory pages and pagemap operations, so a
BAR1 policy must not force UVM coherence or overwrite pagemap ownership to
make a P2P path appear available.

### Porting consequence

The clean branch may prevent static BAR1 from being registered as a Linux
P2PDMA provider when that registration would replace incompatible pagemap
operations, but it must retain the official devmem eligibility helper and HMM
retry behavior unchanged.

## RM P2P capability handling

The system P2P capability interface still reports access, atomics, NVLink,
and PCI BAR1 independently. For NVLink, 610.57.04 no longer asserts that RM
returns exactly one optimal write copy engine. It selects the lowest set bit
and documents that the UVM interface cannot yet represent multiple engines.

This is a robustness change for NVLink capability consumption, not permission
to synthesize PCIe BAR1 support. The clean implementation must continue to
require both read and write support and must not change atomic capability by
encoding a blanket registry override.

## Generated HAL capability tables

The relevant BAR1 P2P dispatch tables did not acquire the broad fallback used
by the rejected feature patch. The official tables already dispatch the GH100
BAR1 implementation for the supported GH100/GB100/GB10B/GB11x/GB20x/GR10x
set, and `PDB_PROP_KBUS_SUPPORT_BAR1_P2P_BY_DEFAULT` already covers the
officially enabled GB20x/GR10x implementations.

### Porting consequence

The clean branch must have no changes under `src/nvidia/generated/` for this
feature. Ampere or Ada support, if pursued later, needs an explicit reviewed
implementation and cannot be obtained by sending every unsupported chip to
GH100 handlers.

## Additional lifetime and robustness changes

- RM device destruction releases the session device-tree lock before freeing
  the RM device object and its lock.
- DMA-BUF handle duplication and BAR mapping allocate thread state dynamically
  and return `NV_ERR_NO_MEMORY` when it cannot be created.
- OS descriptor verification rejects a missing memory descriptor instead of
  dereferencing it.
- GPU virtual-address page-size selection adds an alignment constraint between
  VA offset and physical offset. This matters when a peer or external mapping
  attempts to select large pages.

These are release invariants and must not be reverted while resolving porting
conflicts.

## Old-branch disposition matrix

| Old change | 610.57.04 disposition |
| --- | --- |
| Global P2P read/write and BAR1 defaults | Drop. Preserve official defaults and registry precedence. |
| Forced Resizable BAR default | Drop. Configuration is platform policy, not a feature prerequisite to hard-code. |
| Generated GH100 fallback dispatch | Drop. Official GB20x dispatch exists; unsupported chips remain unsupported. |
| GP100-level BAR1 routing for all older chips | Drop from this branch. Revisit only as an independently reviewed Ampere/Ada feature. |
| Forced UVM coherence for Blackwell | Drop. Preserve official coherence reporting and use a narrow P2PDMA registration guard if required. |
| Disabled IOVA assertions/diagnostics | Drop. A null-safe diagnostic may be added independently without suppressing lifetime errors. |
| Dead `bar1BusAddr` PTE plumbing and its cleanup | Drop both. The clean base never introduces it. |
| Hugepage page-array compression experiment | Defer. It must be redesigned around 610.57.04 ownership, DMA direction, and IOMMU rules. |
| Transactional mailbox P2P setup | Port and retest. It is independent safety work. |
| Runtime static-BAR1 coverage and range checks | Port against official GB20x properties and current RM mapping code. |
| UVM static-BAR1 P2PDMA exclusion | Port narrowly without changing `uvm_gpu_supports_devmem()`. |
| FORCE_PCIE physical-address serialization | Port around the corrected 610.57.04 refcount/unwind logic. |
| Default-off non-coherent DMA-BUF policy | Port with runtime predicates and no device-ID allowlist. |
| Importer DMA-mask/IOMMU/P2PDMA validation | Port using the corrected modern-IOMMU classification and fail-closed semantics. |
| Old install helper | Omit. It is absent from the official base and executes privileged host operations. |

## Required validation

Sandbox-safe validation consists of standalone policy tests, compile checks,
source invariants, ancestry checks, and module builds when matching kernel
headers are available. Live CUDA, NCCL, `nvidia-smi`, PCI topology, and DMA
counter validation require a GPU host and are not represented as sandbox
passes.
